# OmniPad 连接二维码载荷 v1

> 这份文档定义**服务端画出来的二维码里到底装了什么**。它和 [protocol.md](protocol.md)
> 是两件事：那份文档管 TCP 上的 JSON 消息，这份管「扫码配对」这条**旁路**。
> 之所以单独成文而不是塞进 protocol.md，是因为它不经过 TCP —— 二维码是屏幕到摄像头，
> 双端在这里交换的是一段文本，不是协议帧。
>
> 但它仍然是**双端接口**，按 `AGENTS.md` 的接口约束：先改本文档，再改代码。

---

## 为什么要二维码

手动配对要在手机上敲三样东西：地址、端口、8 位配对令牌。令牌的字母表刻意剔除了
易混淆字符，代价是「看起来像乱码」，手输八位出错率高，错一位得到的还是
`AUTH_FAILED` —— 用户以为自己填对了。

二维码把这三样一次带过去，同时带上了**协议版本**。这一点顺手解决了
[fix.md](../fix.md) 第 32 条留下的问题：旧版 App 连新版服务端时，过去会先过版本检查、
再倒在令牌校验上，用户看到 `AUTH_FAILED` 以为令牌错了，真实原因却是 App 太旧。
现在客户端在**扫码那一刻**就知道版本对不上，可以直说「请更新 App」。

## 载荷形态

```
omnipad://pair?v=1.1&host=192.168.1.5&port=5800&token=K7M2P9QR&name=DESKTOP-ABC
```

- 固定 scheme `omnipad`、固定动作 `pair`
- 全部信息放在查询串里，**没有**路径段与片段（`#` 之后的内容一律忽略）
- 用 `://` 之后、`?` 之前的部分判定动作，大小写不敏感

选 URI 而不是裸 JSON 或 `host:port:token` 拼接，原因有三：
通用扫码 App 扫到会显示成一条可读链接而不是一串乱码；将来加字段不用改格式；
客户端可以把同一段文本从剪贴板粘进来，走完全相同的解析路径。

---

## 字段

| 字段 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `v` | 是 | `1.1` 这类协议版本 | **协议**版本，不是 App 版本。见 [protocol.md](protocol.md#协议版本与兼容性) |
| `host` | 是 | IPv4 / 主机名 / `[IPv6]` | 手机要连的地址。服务端从本机可用地址里挑一个 |
| `port` | 是 | `1`–`65535` | 十进制，不接受 `0` 与空串 |
| `token` | 是 | 8 位配对令牌 | 与服务端 `pairing_token.txt` 一致；见 protocol.md 的「配对令牌」 |
| `name` | 否 | ≤ 64 字节 | 电脑名，仅用于界面显示（「连接到 DESKTOP-ABC」），**不参与连接** |

字段名大小写敏感（全小写）。

### 规范编码顺序

生成方必须按 `v` `host` `port` `token` `name` 的顺序输出。同样的连接参数必须产出
**逐字节相同**的载荷 —— 否则二维码每次重绘都不一样，测试也没法比对。

### 载荷长度

整个 URI 必须 ≤ **300 字节**，`name` 字段本身 ≤ **64 字节**。两条限制的处理方式不同：

- `name` 超长 → 按 **UTF-8 字符边界**截到 64 字节（它只是显示用的名字，
  截断无害，但绝不能把一个字符劈成半个）
- 整条 URI 仍然超长 → **整个丢掉 `name`**，而不是截断 URI ——
  截断后的载荷是无效的，对方只会解析失败

`v`/`host`/`port`/`token` 四项加起来上界约 100 字节，所以 300 这条实际只约束
主机名离谱的长的情况。

300 字节对应 byte 模式下的 QR version 10（纠错等级 M），33×33 起步的码点密度
仍然很好扫；再往上加字段就该考虑换 version 了。

## 编解码规则

1. 文本按 **UTF-8** 编码；百分号编码的转义对象是**字节**，不是字符。
2. 需要转义的字节：所有不在 `A-Za-z0-9-._~` 里的字节，包括 `&` `=` `%` 空格与非 ASCII。
   十六进制用**大写**（`%2F` 而不是 `%2f`）。
3. 空格必须编码成 `%20`，**不允许**用 `+` 表示空格。
4. 解码方**不得**把 `+` 还原成空格 —— 那样 `token` 里合法的 `+` 会被静默改写。
   这是本项目里唯一一处刻意偏离 `application/x-www-form-urlencoded` 的地方，
   因为令牌字母表虽然不含 `+`，将来却可能放宽。
5. 解码顺序：先按 `&` 切参数，再按**第一个** `=` 切键值，最后百分号解码。
   值里出现 `=` 是合法的（它会被当成值的一部分）。

## 拒绝规则

客户端解析失败时必须给出**分类**，不能笼统地说「二维码无效」：

| 分类 | 触发条件 | 界面该说什么 |
|---|---|---|
| `NotOmniPadLink` | scheme 不是 `omnipad`，或动作不是 `pair` | 「这不是 OmniPad 的连接二维码」 |
| `MissingField` | 必填字段缺失 | 「二维码内容不完整，请在电脑上重新显示」 |
| `DuplicateField` | 同一字段出现两次 | 同上（歧义不猜，宁可让用户重扫） |
| `BadPort` | 非十进制 / 越界 | 「二维码里的端口不合法」 |
| `BadHost` | 不满足 `EndpointValidator` 的主机规则 | 「二维码里的地址不合法」 |
| `BadToken` | 空 / 含空白 | 「二维码里的配对令牌不合法」 |
| `VersionMismatch` | `v` 与 App 的协议版本不同 | 「二维码来自 vX 的服务端，请更新 App」 |
| `TooLong` | 整段 > 2048 字节 | 「二维码内容异常，已忽略」 |

`TooLong` 的 2048 是个纯防御性上限：正常载荷只有几十字节，扫到超长内容说明
对面根本不是 OmniPad。

**未知字段一律忽略**，不报错。这一条与 protocol.md 里 `additionalProperties: false`
的严格立场相反，是有意的：二维码可能是**更新版服务端**画出来的，多一个字段就报错
会让「新服务端 + 旧 App」直接不可用；而协议版本已经由 `v` 卡住了破坏性变更，
未知字段再多也改不了已有字段的语义。

## 服务端怎么产出它

- 载荷由 `server/qr.py` 的 `build_payload()` 生成，**唯一一份**实现。
- 图形界面在顶部显示二维码，并提供地址切换 —— 装了 Tailscale 的机器有多个可用地址，
  手机在局域网里要选局域网地址，在外面要选 Tailscale 地址。**当前选中的那个地址
  就是要写进二维码的地址**，界面必须把这件事写清楚。
- 无头模式在启动横幅里打印载荷文本，并把二维码画在终端里、另存一份
  `pairing_qr.png` 到数据目录。
- `--status --json` 与状态文件里有 `qr_payload` 字段（纯文本）。
  但 `--status` 的**人读**输出里没有 —— 那份输出是给人贴进 issue 的，
  而载荷含明文令牌。见 `docs/server-cli.md`。

## 客户端怎么消费它

- 只用**自带的扫码窗口**扫（连接页底部弹出的半屏面板），不接受系统相机跳转。
- 扫到之后的处理**等同于手动输入**：把 `host` / `port` / `token` 填进连接页的三个框，
  校验规则与手输完全一致（`EndpointValidator`），然后发起连接。
- `name` 只用于提示文案，例如「正在连接 DESKTOP-ABC…」。

---

## 安全

二维码里**明文包含配对令牌**。它和电脑屏幕上那行令牌是同一份秘密，所以：

- 不要把二维码截图发到群里 —— 那等于把令牌发出去
- 令牌被泄露的后果是「局域网内有人能控制你的鼠标键盘」，与 protocol.md 里的
  威胁模型一致（当前不做 TLS，见 fix.md 第 30 条）
- 通用扫码 App 扫到会显示成一条链接，令牌因此可能进入相册/通知/剪贴板历史。
  这也是客户端**只用自己的扫码窗口**、并把扫到的原文留在内存里的原因之一

## 示例

最小可用载荷：

```
omnipad://pair?v=1.1&host=192.168.1.5&port=5800&token=K7M2P9QR
```

带电脑名（名字里有空格，必须转义成 `%20`）：

```
omnipad://pair?v=1.1&host=192.168.1.5&port=5800&token=K7M2P9QR&name=HAICHUAN%20PC
```

Tailscale 地址：

```
omnipad://pair?v=1.1&host=100.101.102.103&port=5800&token=K7M2P9QR&name=DESKTOP-ABC
```
